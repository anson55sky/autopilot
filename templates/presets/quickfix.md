## 验收矩阵 · preset=quickfix（修一个已复现的问题）

起步前提：问题**已经能稳定复现**。复现不出来，先用 `feature` 档的 A0 把复现固化下来，
不要直接开修——凭猜改代码是本档最常见的失效方式。

| # | 验收条目 | 判定方式（写进 `.autopilot/checks/run.sh`） |
| --- | --- | --- |
| A1 | 复现脚本在改动前必然失败 | `sh checks/repro.sh`（基线那次跑出非零才算有效；本次不要求通过，只要求"曾经是红的"） |
| A2 | 改动后同一脚本通过 | `sh checks/repro.sh` 退 0 且 `RESULT A2 PASS <输出末行>` |
| A3 | 原问题所在路径的行为断言 | 针对症状本身写一条：如"重开窗口后侧栏文件夹框不再闪"→ 断言首帧状态/尺寸，不接受"看起来好了" |
| A4 | 既有测试与验收全绿、无新增失败项 | `sh checks/run.sh all`；退出码 0 且 FAIL 计数为 0（SKIP 单列，不算绿） |
| A5 | 没有引入新的告警/回归面 | 编译或 lint 输出与基线做集合差：新增行数为 0（基线已存在的旧告警不算违反） |

## 非目标（本档默认排除，需要就先换档）

重构周边代码、顺手改命名、补无关测试、性能优化、改既有测试的预期值让它通过（改测试判为违规）。

## 常见盲区（REPORT 必须逐条回答）

- A3 是不是只测了"这次触发的那一条路径"？同函数的其他调用点有没有受影响？
- 修的是症状还是前提？同一前提修两次仍过不了同一关 → 触发 Triage 前提置疑规程，停机置疑，不要开第三次修。
- 不可逆动作（发版、push、清数据）有没有偷偷执行？一律只写进 inbox 待批。
