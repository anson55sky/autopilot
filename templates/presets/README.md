# 起步档位（H22）

门槛不在"会不会写代码"，而在**能不能把验收写成机器可判定的句子**。三档 preset 各给一套
现成的验收矩阵范式，选一档起步，跑通后再改。`init.sh --preset <名>` 会把对应范式追加进
生成的 `GOAL.md`；不加 `--preset` 时 `GOAL.md` 与旧版逐字节一致。

| 档 | 什么时候用 | 预算档位 | 文件 |
| --- | --- | --- | --- |
| `quickfix` | 修一个已复现的 bug、加一个小行为、单文件改动 | 轮 3 / 卡 3 / 并行 1 / 45 分钟 | `quickfix.md` |
| `feature` | 一个完整功能（含界面或接口），能一次验收讲清 | 轮 8 / 卡 5 / 并行 2 / 3 小时 | `feature.md` |
| `longrun` | 克隆 / 重构 / 迁移，几十条验收、跨会话几十轮 | 轮 30+ / 卡 8 / 并行 3 / 8 小时 | `longrun.md` |

## 每档都遵守的四条

1. **每条验收都能被一条命令判定**——句式统一为 `RESULT <A#> PASS|FAIL|SKIP <一句话证据>`。
   写不出命令的那条，就不是验收，是愿望，删掉或改写到能写出来为止。
2. **先有失败再有通过**（铁律 1）：矩阵第一条必须是"当前状态下 FAIL 可复现"，
   否则无法证明是这次改动让它过的。
3. **SKIP 不是通过**：环境缺项判 SKIP，REPORT 必须单列并附环境声明。
4. **不可逆动作只进 inbox**：push / 发布 / 付费调用 / 删数据一律不执行，写清待批命令。

## 选错档的代价

按 `quickfix` 起步却做出 300 行改动 → 卡规模上限（H10）会警告，且验收矩阵覆盖不住；
按 `longrun` 起步只修一个 bug → 预算和闸门空转，一轮收不下任何有效进展。
中途可以换档，但**换档属于契约变更**：走 `proposal_merge.py`，本 run 不生效（铁律：run 内不放宽矩阵）。
