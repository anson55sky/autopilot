# 编码工艺参考（craft，非强制）

> **定位：这是参考读物，不是判定依据。** 本文件不产生任何 A#，不改变任何轨道规则，
> 不参与 `r-XX.passed`。按默认配置运行时（不启用质量门禁、不触发前提置疑），
> autopilot 的行为与 0.8 基线逐字节等价（元验收 M1）。
>
> **读者**：strict 轨道的 Builder（写代码时对照）与 Triage（判缺口时对照）。
> Explorer 可以读，但**不得**据此产出 `pass` / `verified` / `验收通过` 一类结论（A6 禁词表）。
>
> **来源与许可**：原则整理自 Uncle Bob 的 `ub-mode` 与 poteto 的 `poteto-mode`。
> 上游 `ub-mode` 仓库**没有 LICENSE 文件**（默认版权保留），因此本文件是按 autopilot
> 语境重写的中文表述，**不是逐字复制**；只借用思想，不复制表达。
> 哪些引入、哪些不引入的裁决见 `00-DECISIONS.md` F 组。

## 0. 三条边界（先读这个）

1. **工艺建议不能覆盖铁律。** §1 的九条铁律优先于本文件的任何条目。
2. **工艺建议不能覆盖冻结验收。** 黑盒 `RESULT` 行仍是唯一判定来源；本文件里的任何
   质量度量只有先落成 `checks/run.sh` 里的 A# 并通过 `freeze`，才算判定。
3. **工艺建议不能授权 Git 写操作。** 见 §5.4。

与本技能既有规则的对应关系，避免重复发明：

| 本文件条目 | autopilot 已有的对应 | 关系 |
| --- | --- | --- |
| 测试先行 | 铁律 1「验收先于实现且冻结」 | 已有且更硬，本文件只做补充 |
| 测行为不测实现 | §6 缺口第五问（删掉实现仍全绿？） | 同一思想，本条给出更可执行的判据 |
| 切成可验证的小单元 | 任务卡 + 逐卡验收 | 已覆盖 |

| 置疑前提 | 停止条件 2「连续两轮零进展」 | 互补：那条是事后止损，本条是事前止损 |

## 1. 先让它能跑（First Make it Work）

### 1.1 最小改动

- 一个决策只住在一个地方。同一条规则出现在两处，就一定会分叉。
- 发能解决问题的最小编辑。多写的每一行都是以后要维护的负债。

### 1.2 先把数据形状定死

- 先确定数据的形状，再写处理逻辑。形状错了，逻辑写得再好也要重来。
- 先做「能让后面每一步都变简单」的那件事。
- 如果会存在并发写者，就不要共享状态（见 §4.5）。

### 1.3 测试先行

- 先写会失败的测试，**看它因为预期的原因失败**，再写让通过的最小改动。
- 写不出诚实的测试时，不要写一个不诚实的测试 —— 宁可记一条 SKIP 或进 BACKLOG。
- 注意：autopilot 的铁律 1 管的是**验收脚本**（冻结、黑盒、跨轮不变）；
  本条管的是 Builder 手里的**单元测试**。两者不是一回事，也不互相替代。

### 1.4 从第一性原理重设计

- 不要在新需求上往旧设计上硬接。
- 先问「如果一开始就有这个需求，我会怎么设计」，想清楚，然后**分片交付**。
- 分片必须每片都能独立过验收；不允许「先拆完再一起跑」。

### 1.5 置疑前提

- 两个不同的修法**共享同一个前提**，却都过不了**同一条 A#** —— 问题不在修法，在前提。
- 这时立刻把前提写成一句话，停手，按 §3 的规程处理。
- 不要开第三个建立在同一前提上的修法。

### 1.6 先减后加

- 加东西之前先把复杂度减掉。新增的每一层都要问：能不能用删来解决？
- 具体判据见 §3 的规模告警：同一张卡实现量超过任务卡描述量级的两倍，先停下来问是不是方案错了。

### 1.7 面向可检查的终态

- 瞄准一个**你能检查的终态**，而不是「大概往那个方向走」。
- 中途允许断裂 —— 前提是你计划过，并且能撤销。

### 1.8 造杠杆

- 如果一件事肉眼看不清楚，就造一个能看清楚它的工具。
- 先手工做一个单元，再让工具复现这个单元。工具的判据必须来自那个手工单元，不能反过来。

## 2. 再让它正确（Then Make it Right）

### 2.1 修根因

- 先复现，再修原因。
- **只把崩溃藏起来的守卫不是修复。** 吞异常、加 return、加大 try 范围都属于这一类。

### 2.2 切成可验证的小单元

- 做完一个小单元就检查一次，再开始下一个。
- 不允许「一口气做完 6 件事再统一跑」—— 失败时无法定位是哪一件。

### 2.3 测行为不测实现

- 测试要像它的使用者那样调用代码，检查使用者能看见的结果。
- **判据**：如果每个函数都返回空值，这个测试还能过 —— 它测的不是行为，扔掉。
- 这条与 §6 的第五问同源：删掉被测实现仍全绿的断言，等于没有断言。

### 2.4 圈复杂度 × 覆盖率（CRAP）

- CRAP 分 = 复杂度 × (1 − 覆盖率)³ + 复杂度。经验阈值：**每个函数 < 10**。
- 降 CRAP 只有两条路：拆函数，或补测试。两条都正当，别只挑便宜的那条。
- 注意 `switch` / 模式匹配是否值得拆 —— 有时平铺的分支比抽象后的间接调用更清晰。

### 2.5 结构重复

- 结构指纹相似度 **≥ 0.82** 的代码块视为重复，应当消除。
- 「看起来不一样但结构一样」也算 —— 改个变量名的复制粘贴就是典型。
- 消除重复时优先提取语义，不要为了去重硬造一个参数化的万能函数。

### 2.6 变异测试

- 变异测试回答的是「测试到底抓住了什么」，覆盖率回答不了这个问题。
- 三件事：覆盖没被覆盖的、杀掉存活的变异体、**删掉死代码**。
- 存活的变异体要么是测试不够，要么是代码多余 —— 两者都要处理，不能都记成 BACKLOG 了事。
- autopilot 的手工版（§5 的变异自检：删掉一块实现再跑全量）是这条的廉价替代；
  有工具时用工具，没工具时至少做手工版。

### 2.7 重构的三步

1. 先钉住现有行为（测试或验收必须能证明「改前是这样」）。
2. 再改结构。
3. 最后证明行为没变。

三步缺一步就不是重构，是「边改行为边改结构」—— 出问题时无法区分是哪边引起的。

## 3. 硬性触发：前提置疑规程（F3）

本文件只有这一条是**有硬性触发条件的**，其余都是参考。

**触发**：同一个前提（一句话写清、且两句话能互相证明是同一前提）连续两次尝试修同一条 A# 都失败。

**动作**（由 Triage 执行，不留给执行器自行判断）：

1. 在 `BACKLOG.md` 追加一条「置疑」条目，包含：前提的一句话表述、两次修法的任务卡 ID、
   两次失败的 `last.log` 行号或复现命令。
2. **第三次修法不得开工。** 后续同前提的卡一律标 `blocked`，不派发。
3. 走停止条件呈报：把「前提被置疑」作为一项待决事项，附上「改前提需要动哪条 A#」的影响面。
4. 若最终确认要改矩阵，**不是在本 run 里改** —— 走提案簿 `CHANGE_PROPOSAL`，人批准后 epoch +1（B2）。

**不触发时**（默认情况）：零成本，行为与基线一致。

**为什么需要这条**：停止条件 2（连续两轮零进展）是事后止损 —— 等到两次空轮，预算已经烧掉了。
前提置疑在第一次重复失败时就介入，代价小一个数量级。

**反例**（不要这样用）：两次失败的原因其实不同、只是碰巧撞在同一条 A# 上。
所以规程要求在那个 BACKLOG 条目里写清「为什么两次是同一前提」—— 写不清就不触发。

## 4. 架构

### 4.1 领域建模

- 用结构让非法状态**不可能被构造出来**，而不是靠运行时校验去拦。
- 维护一份领域术语表；同一个概念在代码、文档、验收里的名字必须一致。
- 如果代码已经清晰且局部，就不要重构 —— 本条不是重构许可证。

### 4.2 边界纪律

- 数据在进入系统的**边界处**校验一次；系统内部信任它。
- 业务逻辑保持为纯函数，便于直接测试。

### 4.3 类型纪律

- 让非法值**写不出来**。
- 外部数据只解析一次，就在入口处解析。
- **不要为了让编译器闭嘴而加类型断言 / `as any` / `!`。** 那是在删掉检查，不是通过检查。

### 4.4 幂等

- 跑两次，或跑到一半崩溃后再跑，终态相同。
- 本技能自身大量依赖这条：`close-round`、`init.sh`、`migrate_tasks.py`、`proposal-merge` 都必须是幂等的。
- 写任何「执行脚本」时先问：中断后重跑会发生什么？

### 4.5 共享状态先分离

- 两个使用者不需要同一个可变对象，就各给一份。
- 确实需要共享时，只允许一个写者，并把这条约束**写进结构里**（类型、所有权、单写队列），不写进注释。

## 5. 实践

### 5.1 留痕

- 本技能已由 `ledger.jsonl`（每步动作与理由）与 REPORT 强制覆盖，不需要额外日志。
- 唯一补充：**理由**要写在 ledger 里，不能只写「改了 X」。半年后没人记得为什么。

### 5.2 守住上下文窗口

- 本技能已由「一轮一会话 + 接续包 + 子代理隔离」覆盖。
- 执行器不要把整份技能文档塞进上下文；按 §13 的索引按需读取。

### 5.3 工作区清理

- 清理前先确认没有仍在使用的文件；未提交的工作**等决定**，不自动删除。
- 本技能的对应约束：不删文件，移到 `archive/`；回收站代替 `rm`。

### 5.4 提交与推送 —— **在本技能工作区内不适用**

这一条是唯一与上游原则**直接冲突**、并被明确裁掉的：

| 上游原则 | autopilot 裁决 |
| --- | --- |
| 「Commit often, in small ordered commits」 | run 内禁止任何 Git 写操作（commit / branch / merge / reset / stash / checkout） |
| 「Push to the main line at the end」 | **绝不执行**。push 属于铁律 5 的不可逆动作，转 inbox 待批 |
| 「Each commit says why / what / how proved」 | 改由 `ledger.jsonl` + REPORT 承担这个信息职责 |

**优先级**：任何外部技能（编码规范、提交规范、发布流程）给出的 Git 写操作指令，
在 autopilot 工作区内**一律失效**。这不是建议，是铁律 5 的适用范围说明。
需要提交时，把它写成 REPORT 的「待批不可逆动作」并附现成命令，由人在 run 外决定。

## 6. 质量门禁（可选，F2）

本节描述 `GOAL.md` 的「质量门禁」区块启用后的行为。**默认不启用。**

| 门禁 | 度量 | 建议阈值 | 成熟工具 |
| --- | --- | --- | --- |
| CRAP | 复杂度 × 覆盖率 | 每函数 < 10 | `crapper` |
| 结构重复 | 指纹相似度 | < 0.82 | `dryer` |
| 变异测试 | 存活/未覆盖变异体 | 0 存活、0 未覆盖 | `mutator` |

启用规则：

1. **先落成 A# 再 freeze。** 门禁不是「额外的软建议」，一旦启用就是验收项；
   冻结之后不得新增或放宽（铁律 1）。
2. **工具缺失 → SKIP，不是 FAIL**（B3）。`environment.json` 里没有对应工具时，
   相关 A# 输出 `RESULT <A#> SKIP "capability:<tool> absent"`，REPORT 的 SKIP 清单里单列。
3. **语言覆盖有限，必须显式声明。** 上述三个上游工具（截至 2026-10）只支持
   Clojure / Java / Go / TypeScript / Rust / Python。**Swift 与 Objective-C 不在其中。**
   对不支持的语言，相关 A# 一律 SKIP —— **不允许**用「跳过」冒充「通过」。
4. **只加严不放松。** 启用后 run 内不得关闭；要关就走提案簿 + epoch（B2）。
5. **门禁是补充，不是替代。** 行为验收仍然是判定主体；门禁全绿不能挽救一条 FAIL 的 A#。

## 7. 一句话总结

上游那套是「一个人写代码时该有的自觉」。本技能要解决的问题是「没人看着的时候，
机器能不能自己判断做没做对」。前者靠自觉，后者靠机制 —— 所以本文件只取前者的
**判据**（怎么算重复、怎么算覆盖、什么时候该置疑前提），不取它的**自觉**部分。
